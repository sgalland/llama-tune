# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`llama-tune` is a Rust TUI (ratatui + crossterm) that detects the local machine's hardware (CPU, RAM, GPU/VRAM) and computes recommended `llama.cpp` CLI parameters (`-ngl`, `--ctx-size`, `--threads`, `--batch-size`, etc.), and also queries the HuggingFace API for GGUF models that fit within detected VRAM/RAM.

## Commands

```sh
cargo build                        # debug build (nvidia feature on by default)
cargo build --release              # release build
cargo run                          # run the TUI
cargo build --no-default-features  # build without NVML-based NVIDIA VRAM detection (DXGI/sysfs cross-vendor detection is always compiled in)
cargo check                        # fast type-check
cargo clippy                       # lint
cargo test                         # run unit tests
```

Unit tests live in `#[cfg(test)] mod tests` blocks at the bottom of each source file (this is a binary-only crate — no `lib.rs` — so `cargo test`, not `cargo test --lib`, is what runs them). Coverage focuses on pure logic and filesystem operations parameterized by an explicit path (`installed.rs`'s `pick_model_gguf`/`hf_repo_cached`, tested via `tempfile`-created directories; `launch.rs`'s `resolve_executable`/`is_unified_binary`). Deliberately untested: anything that touches the developer's real config file or env vars (`Config::load`/`save`/`config_path`, `scan_installed`/`scan_all_installed`/`hf_hub_cache_dir`, which key off `HUGGINGFACE_HUB_CACHE`/`HF_HOME`/`LLAMA_TUNE_MODELS_DIR`), spawns a real process (`spawn_llama_cpp`), or makes real network calls (`fetch_recommended_models`/`search_models`/`fetch_installed_models` in `models.rs`) — plus `main.rs`'s event-loop glue and `ui.rs`'s `ratatui` rendering, both exercised instead by manually running the TUI. `App` in tests is built via a direct struct literal (not `App::new()`, which calls `Config::load()`).

## Architecture

The app follows a single-directional data flow: async detection tasks feed a channel, the main loop drains the channel into `App` state, then redraws the UI every tick. Ten modules, each with one responsibility:

- **`main.rs`** — owns the terminal (raw mode / alternate screen setup+teardown via crossterm), the `tokio` event loop, and an `mpsc` channel (`AppMsg`) that carries results back from spawned async tasks (hardware detection, model fetch, installed-model scan, model download progress/completion/error/cancellation, launch monitoring). Input handling (key bindings) and message draining both happen once per loop iteration; `ui::draw` is called every iteration regardless of new data. `spawn_model_fetch(hw, query, tx, http)` picks `models::search_models` (`query: Some`) vs `models::fetch_recommended_models` (`query: None`) and is shared by the initial hardware-ready fetch, `[r]` refresh, and search submission, so a refresh preserves whatever search is currently active instead of silently dropping it. `spawn_installed_scan(tx, http)` (called at startup and again on `[r]`, independent of hardware detection and the search box) runs the blocking full hub-cache scan (`installed::scan_all_installed`) via `spawn_blocking`, sends `AppMsg::InstalledScanned` immediately (id -> path, no network), then fetches full metadata via `models::fetch_installed_models` and sends `AppMsg::InstalledModelsReady` — this is what keeps installed models visible in the Models tab regardless of the active search (see `App::display_models`, app.rs). `AppMsg::InstalledScanned` is *merged* into `App.installed` (`.extend`, not replace) since it now arrives from two independent sources (this full-cache scan, and the per-search-list scan fired off from `AppMsg::ModelsReady`); `[r]` refresh clears `app.installed`/`app.installed_models` up front instead, so a since-uninstalled model doesn't linger as stale. Pressing `r` re-triggers hardware detection, model fetch, and the installed scan. Key events are filtered to ignore `KeyEventKind::Release` — Windows (unlike Unix terminals) reports both press and release for every key, so without this filter every keypress would fire its handler twice. Every genuine keypress (post-filter) first clears `App.launch_status` to `None`, so a launch/download status message shown in the status bar (see `ui.rs`) doesn't linger forever — whatever that keypress does, if anything, can still set a fresh message right after. When the Settings tab is in edit mode, keystrokes are routed to the input buffer instead of the global keybindings; the Models tab search box (opened with `/`, via `App::start_search`) works the same way while `app.search_editing` is set — `Enter` submits (empty input clears `search_query` back to `None`, reverting to the recommended list; non-empty re-fetches via `spawn_model_fetch`) and `Esc` calls `App::cancel_search_editing`. `l` (Models tab) calls the free function `launch_or_download`, which launches immediately via `App::launch_now` if the model is already in `App.installed`, otherwise validates the configured llama.cpp path up front via `launch::resolve_executable` (`pub(crate)`, same check `launch_now` uses) before starting anything — a bad path used to only surface its error after a full (potentially multi-gigabyte) download finished, which looked identical to no error at all to anyone who didn't wait that long — and only once that passes does it create a shared `Arc<AtomicBool>` cancel flag, store it on `App.download`, and spawn a task calling `download::download_to_cache` that launches automatically on `AppMsg::DownloadComplete`. `AppMsg::DownloadComplete` carries the full `HfModel` it was downloading (`{ model: HfModel, path: PathBuf }`), not just its id — moved into the spawned task from the same `HfModel` `launch_or_download` already had in hand, so the completion handler can call `app.launch_now(&model, &path)` directly instead of re-deriving it via `App::find_model`/`display_models()`; right after a fresh download, the model is briefly excluded from *both* halves of that merged list (no longer a search/recommended result now that it's "installed", not yet in `installed_models`, which only arrives via the separate, slower `spawn_installed_scan`), so a `find_model` lookup at that moment used to return `None` and silently skip the auto-launch. `L` (any tab) calls `relaunch_last`, which looks up `Config::last_launched_model_id` via `App::find_model` and re-runs `launch_or_download`. `x` (only meaningful while `App.download` is `Some`) sets the download's cancel flag; the spawned task notices between chunks, and the caller distinguishes a user-requested cancellation from a genuine failure by checking that same `Arc<AtomicBool>` after the awaited call errors (not by string-matching the error), sending `AppMsg::DownloadCancelled` vs `AppMsg::DownloadError` accordingly. `AppMsg::DownloadProgress` updates the existing `DownloadState` in place rather than reconstructing it, so the shared `cancel` flag isn't replaced with a disconnected one. Both call sites of `App::launch_now` (in `launch_or_download` and the `AppMsg::DownloadComplete` handler) pass its returned `Child` to `monitor_launch`, which polls `Child::try_wait` every 200ms for a 3-second grace period and sends `AppMsg::LaunchExitedEarly { model_id, code }` if the process dies unsuccessfully within that window — a process still running after the grace period is assumed healthy and isn't polled further.
- **`app.rs`** — holds all UI/application state (`App` struct): current tab (now `Hardware`/`Parameters`/`Models`/`Settings`), `LoadState<T>` (Loading/Ready/Error) wrappers for hardware and models, computed params, the model list's `ListState`, persisted `Config`, `installed: HashMap<String, PathBuf>` mapping installed model IDs to their local GGUF file (not just a presence set — the path is needed to launch), `installed_models: Vec<HfModel>` (full metadata for installed models, fetched independently of `models_state` — see `display_models` below), `search_query`/`search_editing`/`search_input` (the Models tab search box's active query and edit-mode buffer, mirroring the Settings-tab edit-mode fields), and `download: Option<DownloadState>` tracking the single in-flight download (if any) for progress display, where `DownloadState.cancel: Arc<AtomicBool>` is the shared flag `main.rs`'s `x` key sets and `download_to_cache` polls between chunks. No async I/O happens here — it's state plus small mutation methods. `display_models(&self) -> Vec<&HfModel>` is the Models tab's actual list contents: `installed_models` first (but only when `search_query.is_none()` — a search is for finding something new, so re-surfacing an already-installed match there would just be noise; the plain Recommendations view still shows them), then whatever `models_state` currently holds (search results or the recommended list) filtered to exclude ids already in `installed` — so a model stays visible after being downloaded even if it later falls out of the active search/recommended ranking. `next_model`/`prev_model` (which also call `recompute_params`), `selected_model`, and `find_model` (looks up any model by id regardless of current UI selection, used for relaunch) all index into `display_models()` rather than `models_state` directly, so selection/launch/relaunch work uniformly across the merged list. `start_search`/`cancel_search_editing` manage the search box's edit mode (seeding `search_input` from any currently-active `search_query` on entry), the Settings-tab edit-mode methods (`start_editing_path`/`cancel_editing_path`/`confirm_editing_path`, which persist via `Config::save`), and `launch_now(model, path)` (computes params for that *specific* model — not `self.params`, which only tracks the UI selection — calls `launch::spawn_llama_cpp`, stores the outcome in `launch_status`, and on success persists `model.model_id` as `Config::last_launched_model_id`). Returns the spawned `std::process::Child` on success (`None` on failure) so `main.rs` can watch for an early exit — `launch_now` itself only knows the process *started*, not that it kept running.
- **`hardware.rs`** — `detect()` builds a `HardwareInfo` snapshot using `sysinfo` for CPU/RAM only — `sysinfo` has no GPU API at any version, despite what an old comment used to claim. GPU detection is per-vendor/per-platform, run in `detect_gpus()`: NVML (via `nvml-wrapper`, the `nvidia` feature, on by default) for NVIDIA VRAM; a macOS `sysctl`-based fallback that treats Apple Silicon unified memory as VRAM when no GPU was otherwise found; on Windows, `detect_windows_dxgi()` enumerates all adapters via DXGI (the `windows` crate, scoped to `[target.'cfg(windows)'.dependencies]` in Cargo.toml) and covers AMD/Intel/other vendors by PCI `VendorId`, skipping the entry if NVML already reported an NVIDIA GPU (NVML's numbers are more precise — exact free/used memory, not just the OS-reported dedicated-VRAM figure). Reported VRAM is `DedicatedVideoMemory.max(SharedSystemMemory)`, not `DedicatedVideoMemory` alone — integrated GPUs (Intel especially) report a tiny dedicated figure (a BIOS-reserved aperture, ~128MB) but a large shared figure (the real budget the driver draws from system RAM), the reverse of discrete GPUs, so taking the max picks whichever field is actually meaningful for that adapter; on Linux, `detect_linux_sysfs_gpus()` reads `/sys/class/drm/card*/device/vendor`: for AMD (`0x1002`) it also reads `mem_info_vram_total` (only `amdgpu` exposes this) and reports a dedicated GPU; for Intel (`0x8086`), since i915/Xe expose no equivalent VRAM-total node (almost all Intel GPUs are integrated with no VRAM chip of their own), it instead reports a non-dedicated entry whose `vram_bytes` is `total_ram_bytes` — the same shared-budget treatment `detect_windows_dxgi`'s `SharedSystemMemory` handling and `detect_apple_silicon` already use — passed down through `detect_gpus(total_ram_bytes)`. This still under/over-reports for discrete Intel Arc cards, which have real VRAM but no sysfs node exposing its size either. `HardwareInfo::total_dedicated_vram_bytes()` sums `vram_bytes` across all detected GPUs (displayed in the Hardware tab's GPU list title, `ui.rs`) — distinct from `primary_vram_bytes()`, which every param-computation heuristic in `params.rs` uses instead.
- **`params.rs`** — pure function `compute(hw, model: Option<&ModelRequirements>)` → `LlamaCppParams`. All parameter choices are heuristic/rule-based (VRAM/RAM thresholds) and each decision pushes a human-readable string into `rationale` so the UI can explain *why* a value was chosen. When a `ModelRequirements` is available, `compute_gpu_layers` estimates how many transformer layers fit in VRAM using `bytes_per_layer` and a rough KV-cache size estimate, reserving ~10% VRAM as overhead headroom, and pushes a rationale line naming `model.quantization` alongside the estimated per-layer size so the UI can explain which quant the VRAM math is based on. Without a selected model, it defaults to `-1` (offload all layers). `to_cli_string()` formats params for display (backslash-newline joined); `to_cli_args()` is the `Vec<String>` sibling used by `launch.rs` to build a `std::process::Command` — don't merge these, one is for showing the user a copyable string, the other for exact argv.
- **`models.rs`** — `fetch_recommended_models` queries `https://huggingface.co/api/models` (GGUF library, sorted by downloads) and filters results to those whose total GGUF sibling file size fits within ~90% of available VRAM (or RAM if no GPU). `search_models(query, hw, client)` is the free-text sibling used by the Models tab search box (`/`) — same `fetch_candidates`/`filter_to_fitting` pipeline, plus HF's `search` query param. `fetch_installed_models(model_ids, client)` fetches full metadata for a fixed list of already-installed ids (no fit-filtering — an install stays visible even if it no longer fits the current hardware budget) and falls back to a minimal id-only stub `HfModel` on a failed per-model lookup, so a local install never disappears from the UI just because HF couldn't be reached; used by `main.rs`'s `spawn_installed_scan`. `HfModel::best_quant_for_memory(budget)` picks the highest-quality quant that fits a memory budget by walking `QUANT_QUALITY_ORDER` (a full lowest-to-highest ordering of llama.cpp's GGUF quant types, `IQ1_S`..`F16`) from the top, falling back to the smallest available quant if none fit. Estimated layer count comes from model name/tags (`estimated_layers`, e.g. "70b" → 80 layers). `download_url_for(quant)` builds the direct HF `resolve/main` download URL for a given quant, which `download.rs` fetches when a model isn't installed yet. `last_modified` (the API's `lastModified` field) is shown as-is (no reformatting) in the Models tab detail panel, `ui.rs`.
- **`installed.rs`** — `scan_installed(models)` does blocking filesystem I/O (called via `spawn_blocking`) to build a `model_id -> PathBuf` map of already-downloaded models, checking the Hugging Face hub cache (`HUGGINGFACE_HUB_CACHE`/`HF_HOME` env vars, else `~/.cache/huggingface/hub`) for `models--org--name/snapshots/*/*.gguf`, plus an optional `LLAMA_TUNE_MODELS_DIR` matched heuristically by normalized filename. Returns the resolved file path (not just a bool) since `launch.rs` needs it to invoke llama.cpp. `scan_all_installed()` is the candidate-list-independent sibling: it enumerates the whole hub cache directly (parsing `models--org--name` folder names back into `org/name` ids) rather than checking specific known models, which is what lets the Models tab show installed models even when they've fallen out of the current search/recommended results — it doesn't cover `LLAMA_TUNE_MODELS_DIR`, since matching an arbitrary local filename back to a model id needs a candidate id to normalize and compare against. Both `scan_installed`'s per-repo lookup (`hf_repo_cached`) and `scan_all_installed` resolve which `.gguf` file to use via the shared `pick_model_gguf(snapshots)` helper: collect every `.gguf` across all snapshots, exclude any with `mmproj` in the filename (case-insensitive — some HF repos ship a `mmproj-*.gguf` multimodal projector file alongside the real weights, meant for `--mmproj`, not `-m`, and unrunnable on its own), then take the largest of what's left (real model weights are always far bigger than a projector), falling back to the largest file overall if filtering leaves nothing. `hf_hub_cache_dir()` is `pub(crate)` so `download.rs` can resolve the same cache root when writing new downloads.
- **`download.rs`** — `download_to_cache(client, model_id, url, tx, cancel)` streams a GGUF file (via `reqwest`'s `bytes_stream()`) straight into the Hugging Face hub cache layout `installed.rs` scans (`models--org--name/snapshots/download/<filename>.gguf` — `download` is a literal placeholder ref, not a real commit hash, but coexists fine since `installed.rs` just looks for any `.gguf` under any snapshot subdirectory). Writes to a `.part` temp file and renames atomically on completion so an interrupted download never leaves a corrupt file at the real path. Issues the GET with a per-request 6-hour `RequestBuilder::timeout` override — the shared `reqwest::Client` in `main.rs` carries a 30s default sized for small JSON API calls, but reqwest's client-level timeout covers the *entire* request including the response body, so without the override every real GGUF download (always well over 30s) would abort partway through. Reports progress by sending `AppMsg::DownloadProgress` after each chunk; the bounded `mpsc` channel naturally throttles how often that happens, so no extra rate-limiting logic was added. Checks `cancel: Arc<AtomicBool>` between chunks; if set, deletes the `.part` file and returns an error, letting the caller (which holds its own clone of the same flag) tell a cancellation apart from a real failure.
- **`config.rs`** — `Config { llama_cpp_path: Option<String>, last_launched_model_id: Option<String> }`, persisted as JSON at `dirs::config_dir()/llama-tune/config.json` via `Config::load()`/`save()`. `load()` degrades to `Config::default()` on any read/parse failure (missing file on first run, corrupt file, etc.) rather than erroring.
- **`launch.rs`** — `spawn_llama_cpp(exe_path, model_path, params)` launches llama.cpp as a **detached** background process (`-m <model_path>` plus `params.to_cli_args()`): on Windows via `CREATE_NEW_CONSOLE` (opens its own console window so output is visible), on Unix by redirecting stdio to `Stdio::null()` (since there's no separate window to attach to and inheriting the TUI's stdio would corrupt the display). `resolve_executable` (`pub(crate)` so `main.rs` can also call it to validate the configured path before starting a download) runs first: if `exe_path` is a directory (e.g. a version-tracking `current` symlink) rather than a file, it searches inside for a known llama.cpp CLI binary name (`llama-cli`, `llama`, `main` — renamed across llama.cpp releases) rather than handing a directory straight to `Command::new`, which fails at the OS level with no window ever appearing. `is_unified_binary` detects the newer consolidated `llama` binary (exact file stem `llama`, as opposed to `llama-cli`/`main`) that dispatches via subcommand (`llama cli -m ...`) instead of taking flags directly — only for that binary, `spawn_llama_cpp` prepends the `cli` subcommand and gives `--flash-attn` an explicit `on` value (that build requires one; older standalone binaries treat it as a bare flag). Returns a short status string plus the spawned `Child` on success; `spawn_llama_cpp` itself still doesn't block on it, but `main.rs`'s `monitor_launch` subsequently polls that `Child` non-blockingly (`try_wait`) for a grace period to catch an early exit.
- **`ui.rs`** — pure rendering (`draw`) driven entirely off `&App`; no state mutation. Four tabs (Hardware/Parameters/Models/Settings) each have a dedicated draw function and separately handle the `LoadState::{Loading,Ready,Error}` cases where applicable. `draw_models` computes `let combined = app.display_models();` up front and renders the list/detail panel from that merged installed+search view, only falling back to the Loading/Error/empty-state placeholders (keyed off `app.models_state`) when `combined` is empty — since `display_models()` no longer prepends installed models during an active search (see `app.rs`), an in-flight search with no results yet genuinely produces an empty `combined`, so this placeholder reliably shows during search loading too, not just the initial recommended-list load. The `Loading` placeholder message is context-aware: `Searching for "<query>"…` when `app.search_query` is `Some`, else the generic `Fetching models from Hugging Face…`. While `app.search_editing` is set, a bordered input row is shown above the list reflecting `app.search_input`; once a search is active (`app.search_query: Some`), the panel title changes to `Model Search: "<query>"` (vs. the default "Model Recommendations") and the empty-results message differentiates ("No models matching ... fit your hardware" vs. the generic message). The Models tab detail panel renders `app.download` progress as a `ratatui::widgets::Gauge` (percentage + bytes if `total` is known, else just bytes downloaded with an empty bar) when it matches the selected model, and the hint line switches between "launch"/"download and launch"/"downloading… press [x] to cancel" based on `app.installed` and `app.download`. The status bar's Models-tab key hint likewise swaps in `[x] Cancel download` while a download is active. The Settings tab shows `Config::last_launched_model_id`. `draw_statusbar` checks `app.download` before `app.launch_status`: if a download is in flight, it renders that progress (bytes/percentage plus an `[x] Cancel` hint) on **every** tab and returns early, since a download's progress keeps changing on its own and the Models tab's `Gauge` only shows it when the downloading model happens to be selected — everywhere else (and everywhere the download's model isn't selected) had no indication one was even running. Otherwise it falls through to the prior behavior: `App.launch_status` (in place of the usual keybinding hints) unconditionally, on every tab including Models — not just other tabs, even though the Models tab detail panel *also* shows it there. That panel is a non-scrolling `Paragraph`; with enough model info/tags/download-URL content pushed above it, the status line (appended last) can get clipped off the bottom of a normal-sized terminal and never render, so the status bar — a single fixed line, always visible regardless of tab content — is the one reliable place for it.

### Key coupling to be aware of

- `HardwareInfo` (hardware.rs) + the selected `HfModel` → `ModelRequirements`/`compute` (params.rs) → `LlamaCppParams` is recomputed via `App::recompute_params` both when hardware/models/installed-models data arrives and whenever the model selection changes (`next_model`/`prev_model` in app.rs, which index into `display_models()`) — so `-ngl` reflects whichever model is currently selected in the Models tab, falling back to a generic "offload all" recommendation when none is selected. `App::launch_now` deliberately recomputes params for the model being launched rather than trusting `self.params`, since relaunching the last-launched model (`L`) may target a model that isn't the one currently selected in the UI.
- `GpuVendor::{Amd, Intel}` are constructed by the Windows DXGI and/or Linux sysfs paths; `Other(String)` is constructed by the Windows DXGI fallback for an unrecognized PCI vendor ID. `Apple` is only constructed by the macOS-specific `detect_apple_silicon` (`#[cfg(target_os = "macos")]`), so non-macOS builds never construct it — it carries a targeted `#[allow(dead_code)]` for that reason rather than being removed. (The enum used to also have an `Unknown` variant with zero producers anywhere, duplicating `Other`'s purpose; it was deleted during a warnings cleanup instead of kept as dead weight.)
- All byte-size math uses raw `u64` bytes with a local `GB` constant (`params.rs`) or `bytesize::ByteSize` for display; don't mix display formatting into the compute functions.
